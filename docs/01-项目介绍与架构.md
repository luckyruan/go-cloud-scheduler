# 项目介绍与架构

## 1. 项目解决什么问题

单机 `cron` 在服务重启、横向扩容和故障恢复时会遇到任务丢失、重复执行、无法追踪等问题。本项目提供一个轻量的分布式调度平台：用户创建 Cron 任务；Scheduler 生成持久化执行记录；多个 Worker 抢占并执行 HTTP 任务；失败后按指数退避重试；Worker 宕机后任务会被其他实例重新接管。

## 2. 架构

```text
Client -> Scheduler API (N replicas) -> PostgreSQL
                    |                       |
                    +-- schedule scan ------+
                                            |
Worker (N replicas) -- claim/heartbeat/result
       |
       +-- HTTP target
```

控制面和执行面解耦。API 与 Worker 都是无状态进程，状态统一落 PostgreSQL，因此可以直接横向扩容。Scheduler 多副本同时扫描时，依赖事务和行级锁保证同一轮任务只被入队一次。

## 3. 核心流程

1. 创建任务时解析 Cron 表达式，计算 `next_run_at`。
2. Scheduler 周期扫描到期任务，在事务内锁定记录，写入 `executions`，并推进下一次运行时间。
3. Worker 调用 Claim API。SQL 使用 `FOR UPDATE SKIP LOCKED`，并发 Worker 不会拿到同一条记录。
4. Claim 将状态原子更新为 `RUNNING`，记录 Worker、时间和新的随机领取 token，同时累计 attempt。
5. Worker 执行期间每 3 秒续租；结果回写必须匹配本轮 token。失败且尚有预算时把同一记录改回 PENDING、推迟 scheduled_at，保留 attempt，不新建重试记录。
6. `RUNNING` 心跳超时且尚有预算时可接管；耗尽预算的最终超时记录落 FAILED。即使没有新候选，清理事务也会提交。

## 4. 一致性语义

项目采用可重投的 at-least-once 设计，但有限重试可能失败终止，不保证永久故障下必达，更不宣称 exactly-once。Worker 可能已完成外部请求、却在上报前宕机，超时后再次执行。当前 Worker 发送稳定 executionId 作为 Idempotency-Key，下游仍须自行实现唯一索引/幂等表；领取 token 只保护本地回写，不阻止旧 HTTP 的副作用。

## 5. 数据模型

- `tasks`：任务定义、Cron、载荷、重试参数、下次触发时间。
- `executions`：一次执行的状态机，状态为 `PENDING/RUNNING/SUCCEEDED/FAILED`。
- `workers`：实例标签、容量和最后心跳，用于可观测性及后续调度策略扩展。

关键索引覆盖 `(status, scheduled_at)` 和 `next_run_at WHERE enabled`，避免扫描全表。

## 6. 可靠性与安全

- 参数化 SQL，API 请求体限制为 1 MiB。
- API Key 鉴权；生产环境应改为短期 JWT/mTLS，并把 Secret 放入密钥系统。
- Worker 只实现 HTTP 执行器，不开放任意 Shell 命令，缩小远程代码执行风险。
- 输出最大保存 16 KiB，防止响应撑爆内存与数据库。
- 优雅退出通过 signal context 完成。

## 7. 可观测性

日志使用 `slog` 结构化输出；Prometheus 暴露领取数和按结果分类的完成数。生产版还应增加调度延迟直方图、队列深度、重试次数、Worker 存活数和 OpenTelemetry Trace。

## 8. 可继续迭代

- Redis/ZooKeeper 选主，或按分片扫描超大任务表。
- 执行日志归档、Web 管理台、RBAC、租户隔离。
- Worker 标签匹配、优先队列、DAG 工作流、暂停与补偿。
- 用 Outbox/消息队列降低数据库轮询压力。
