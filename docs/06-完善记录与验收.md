# 调度器：完善记录与验收

日期：2026-10-04。

## 本轮修复

1. **重试预算**：失败不再插入 attempt=0 的新记录，而是把同一个执行改回 PENDING，保留累计 attempt；maxRetries=1 时最多领取两次。耗尽预算后 FAILED。
2. **领取所有权**：每次 Claim 写入随机 claim_token；心跳与结果必须同时匹配 executionId、workerId、token。相同 Worker ID 重新领取，也不能使用上一轮 token 回写。
3. **长任务续租**：HTTP 执行期间后台每 3 秒续租，每次续租最多 2 秒；失败时保守取消本地请求，等待后台退出。取消不等于撤销已经发生的下游副作用。
4. **最终超时**：最后一次尝试租约过期后落 FAILED；即使没有新候选任务，也提交清理事务。
5. **任务输入**：支持显式 enabled=false，默认仍为 true；名称及超时有边界，拒绝未知字段与拼接多个 JSON，API 不返回原始数据库错误。
6. **HTTP 执行**：默认禁自动重定向；发送稳定 Idempotency-Key 和 X-Scheduler-Execution-ID；读取结果出错不误报成功。下游仍需实现真正去重。
7. 每个 API Server 使用独立指标 Registry，空鉴权密钥不允许访问；Compose 宿主端口绑定 localhost。

## 面试追加题

**为什么稳定 workerId 不够？** 同一进程重启可能复用 ID，旧请求迟到也会匹配；每次领取换随机 token，回写条件才能区分领取轮次。它不是下游可验证的单调 fencing token，不能阻止旧 HTTP 请求的副作用。

**续租能保证只执行一次吗？** 不能。请求执行成功但上报丢失仍会重试；网络抖动也可能触发接管。下游用稳定 executionId 做业务幂等，调度器只保证有限重试与数据库结果所有权。

**为什么无候选也要提交？** Claim 同一事务先清理预算耗尽的过期 RUNNING，再查候选；直接返回并 rollback 会把清理撤销，任务永远停留 RUNNING。
